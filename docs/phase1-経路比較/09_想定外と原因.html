想定外と原因

実行で踏んだ問題 (JSON の破損、欠落の黙殺、Lambda の上限など) と原因・対応

2026-08-22 の実行で踏んだ問題を、発見の順に記録する。コードの不具合として Issue にしたものと、環境の制約として手順に書いたものがある。

011. 経路 B の JSON が引用符で壊れる (4 本中 3 本)

backend の不具合 → #111 で対応済み

論文停止したページエラーそのページの原本にある語句揃ったページ
2608.19529v1p.11invalid character 'B' after object key:value pair"Beauty"14 / 17
2608.19526v1p.3invalid character 'O' after object key:value pair“On ...7 / 15
2608.17950v1p.12invalid character 'p' after object key:value pair“prove...11 / 12
事象
経路 B の BedrockPage が PageDecodeError (bedrock: response is not valid json: ...) で失敗し、Map 全体が止まって未着手のページも処理されない。1 本目 (2608.20338v1) と 2608.20318v1 は通った
原因
bedrock-parser はモデルに「JSON だけを返せ」と指示して応答テキストを json.Unmarshal していた。モデルが本文中の “…” を " のままエスケープせず JSON 文字列に転記すると、パーサは引用句の直前で文字列を閉じ、直後の文字で落ちる。エラーに出る文字 (B / O / p) が引用句の先頭と一致する。引用句のあるページで再現するため、再試行では直らない
対応
Converse の tool use (toolConfig に出力スキーマを登録し toolChoice で強制) で受け取り、Bedrock 側に JSON の整形を任せる (#111、PR #116)。2 回目の実行では同じページが " を含んだまま正しく JSON に入った (2608.19529v1 p.11 の本文に Amazon Beauty³ [23] が残っている)。経路 A も同じ DecodeJSON だったので同時に切り替えた
考慮不足
「JSON だけを返せ」という指示で整形を保証できると見ていた。記録済みレスポンスの再生テストは引用符を含まない合成データだったので、テストでは見つからなかった
022. ページが欠けたまま COMPLETED になる

backend の設計の穴 → #112 で対応済み

事象
1. で Map が止まっても、Step Functions の実行は Catch → BedrockFailed (Pass) を経て Finalize に進み、finalizer は保存済みのページだけで結合して経路 B を succeeded にした。2608.19526v1 は 7 / 15 ページ、参考文献 0 件で COMPLETED / needsReview: false になった
原因
finalize/route.go の bedrockRoute が「ページ結果が 1 件以上あれば成功」と判定し、Catch の Error を見ていなかった。欠落は provenance.warnings に残るだけだった
対応
欠落ページがあるか Catch の Error があれば needsReview: true にし、comparison.json の routes.bedrock に missingPages と error / cause を残す (#112、PR #114)。2 回目の 2608.17950v1 (11 / 12) はこの判定で REVIEW_PENDING になった
033. PageDecodeError を再試行しない

保険として変更 → #113 で対応済み

事象
ステートマシンの BedrockPage は PageDecodeError を InvalidInputError と同じ「再試行しても直らない」扱い (MaxAttempts: 0) にしていた
対応
5 秒後に 1 回だけ再試行する (PR #115、dev に apply 済み)。1 ページ分の課金で経路 B 全体を救える可能性があるため。引用符の問題 (1.) は再試行では直らないので、根本対策ではない。Map の ToleratedFailurePercentage は置かない (欠落のある経路は 2. で再投入が要るため、残りのページにトークンを使っても無駄になる)
結果
2 回目の 2608.17950v1 の p.12 で再試行が走ったが、同じエラー (4.) で 2 回とも失敗した
044. tool use でも型が崩れる (1 ページ)

backend の不具合 → #118 (未対応)

事象
2 回目の 2608.17950v1 の p.12 (見出しの無い本文だけのページ) で、モデルが sections を配列ではなく文字列で返し、json: cannot unmarshal string into Go struct field PageResult.sections of type []bedrockroute.PageSection になった。再試行でも同じ
原因
tool use の inputSchema は strict を付けないと型を保証しない。公式ドキュメントは「strict なしでは型の不一致や必須欠落が起こり得る」とし、strict: true (constrained decoding) を解決策として示している。Claude Sonnet 4.5 は Bedrock Converse で対象
対応 (予定)
strict: true を付け、スキーマの全 object に additionalProperties: false と required を書く。失敗時にモデルの生応答を S3 に残す (今回は何が返ったかが残っておらず、エラー文から推測した)
055. Lambda の同時実行数の上限 (10)

環境の制約 → 01 の前提に記載

事象
2 回目の再投入で 2 本を同時に投げたところ、2608.19526v1 の BedrockPage が 1 回 Lambda.TooManyRequestsException (Rate Exceeded、429) で失敗した。States.TaskFailed の Retry (10 秒後) で回復し、結果には影響していない
原因
このアカウントの Lambda 同時実行数の上限が 10 (get-account-settings)。経路 B の Map が並列 5 なので、2 本で 10 に preprocessor や textract-parser が重なると超える。Bedrock のクォータ (50 リクエスト / 分) より先に当たる
対応
投入は 1 本ずつにする。恒久的には Service Quotas で上限の引き上げを申請する (未実施)
